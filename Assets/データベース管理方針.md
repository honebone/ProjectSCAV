# データベース管理方針

ItemDatabaseの見直しで決定した設計方針のまとめ。今後 Enemy・Area・CraftRecipe など
別のデータベースを実装する際も、この方針をベースに検討する。

## 背景・課題

- 新規実装したデータ(SO)を `XXDatabase` の `SerializeField` リストへ手動登録する必要があり、登録漏れが起きやすい
- `XXDatabase` が ScriptableObject である必然性を再検討したい
- 「特定のフォルダ/ラベルを見れば該当データを勝手に読み込んでくれる」形にしたい

## 最初に確認すること：データベースの性質を見極める

新しいデータベースを作る前に、そのデータベースが次のどちらに当たるか判断する。
**両者を同じ仕組みで解決しようとしない。**

| 種類 | 説明 | 例 | 方針 |
|---|---|---|---|
| 全件データベース | ゲーム内に存在する全アセットをそのまま持つ | ItemDatabase, GunDatabase, EnemyDatabase, CraftRecipeDatabase | 自動収集（Addressablesラベル方式） |
| キュレーションされたデータベース | 意図的に選ばれたサブセットを持つ（バランス調整・演出上の取捨選択が必要） | RoomDatabase（エリアごとの部屋の集合） | 現状維持（SO + 手動アサイン） |

判断基準：「フォルダ内の対象アセットを機械的に全部集めれば良いか？」「それとも人が選ぶ必要があるか？」
迷ったら「新しいアセットを追加したら自動的にゲームに登場してよいか」で判断する。YESなら全件データベース。

## 全件データベースの実装方針

### 採用技術：Addressables（ラベルベース）

- `Resources.LoadAll` ではなく **Addressables** を使う
  - 理由：`Resources` はビルドに焼き込まれたアセットしか対象にできず、DLC/MOD的な外部からのデータ追加に対応できない
  - Addressablesはラベル・カタログベースで管理するため、将来リモートカタログや外部アセットバンドルを追加する拡張にも同じ仕組みの延長で対応できる
- 各データアセットに種類ごとのラベル（`"Item"`, `"Enemy"`, `"CraftRecipe"` 等）を付与し、そのラベルで一括ロードする
- ロードタイミングは **起動時に一括ロードして常駐**（都度ロードではない）。ゲーム中に頻繁に参照する共有データが対象のため

### クラス構成パターン

3つの役割に分割する。**Model層はpure C#に保ち、Unity/Addressables依存はLoaderに閉じ込める。**

```
XXDatabaseModel   [pure C#]
    検索APIのみを持つ（Get, GetByTags 等）
    Dictionary<string, XXData> で保持
    Addressables/UnityEngineに一切依存しない

XXDatabaseLoader  [Unity依存/static]
    Addressables.LoadResourceLocationsAsync(label, typeof(XXData)) で
    対象アセットの所在情報を取得
    ↓
    各locationをAddressables.LoadAssetAsyncでロードし、
    location.PrimaryKey（Addressableのアドレス文字列）をキーとして
    Dictionaryに格納
    ↓
    XXDatabaseModelを構築して返す

GameBootstrapper  [MonoBehaviour]
    起動シーンに配置。Awakeで各XXDatabaseLoader.LoadAsync()を
    まとめて呼び出し、完了を待ってから次のシーンへ遷移
    public static XXDatabaseModel XXDatabase { get; private set; }
    として他のクラスから常駐参照できるようにする
```

参考実装：`ItemDatabaseModel.cs` / `ItemDatabaseLoader.cs` / `GameBootstrapper.cs`

新しいデータベースを追加するときは、`GameBootstrapper.Awake()` 内に
「該当Loaderを呼んで結果を静的プロパティに入れる」処理を追記していく。

### ID管理方針

- 各データの `_id` のような手動文字列フィールドは **廃止**する
- 代わりに **Addressablesのアドレス文字列をIDとして流用**する（`IResourceLocation.PrimaryKey`）
  - 理由：手動IDは重複・入力ミスのリスクがあるが、Addressableアドレスは元から一意性が保証されている
- 注意点：Addressableのデフォルトアドレスはアセットパス（フォルダ込み）になるため、**フォルダ移動でIDが変わる**。
  運用上、アドレス名はファイル名のみ等シンプルな命名にしておくと安全
- 各データに`Id`のような逆引き用フィールドが必要になった場合（セーブデータ書き出し等）は、その時点で改めて検討する

### セットアップ手順（新しい種類のデータベースを追加するたびに行う）

1. （まだなら）Package ManagerでAddressablesを導入
2. 対象アセット（例：`EnemyData`）を選択 → InspectorのAddressableチェックボックスをON
3. Labelsに種類ごとのラベル（例：`"Enemy"`）を追加
   - 既存アセット数が少ないうちは手動でよい。数が増えてきたら「特定フォルダに置いたら自動でラベル付けする」Editor拡張の追加を検討する
4. `XXDatabaseModel` / `XXDatabaseLoader` を実装（`ItemDatabaseModel` / `ItemDatabaseLoader` を雛形にする）
5. `GameBootstrapper.Awake()` にロード処理を追記
6. 旧来の `SerializeField` リスト方式の `XXDatabase`(SO) や、それを参照していた `DatabaseLocator` 経由のコードを置き換える

## キュレーションされたデータベースの実装方針

- 従来通り `ScriptableObject` + `SerializeField` のリストで手動アサインする
- 自動収集の対象にしない（人が意図的に選ぶことに価値があるため）
- 例：`RoomDatabase` は `AreaData` からエリアごとに個別のインスタンスを参照する形を維持

---

## 今回の実装例（ItemDatabase）

- `ItemDatabase`(SO) → 廃止し `ItemDatabaseModel`(pure C#) に置き換え
- `ItemDatabaseLoader` が `"Item"` ラベルのアセット（`ItemData`とその派生型 `GunData` 等）をAddressablesから一括ロード
- `GameBootstrapper` が起動時にロードを待ってから `GameBootstrapper.ItemDatabase` として公開
- `ItemData._id` フィールドを削除し、Addressableアドレスをキーとして利用
- `AreaManager` / `AreaManagerModel` / `LootGeneratorModel` のコンストラクタ引数の型を `ItemDatabase` → `ItemDatabaseModel` に変更
- 不要になった `DatabaseLocator.cs` は削除（他に用途がないため）

## 未解決・今後検討する事項

- セーブデータにアイテム等を永続化する際、Addressableアドレス文字列をそのまま保存してよいか（リネーム耐性）
- アセット数が増えてきた場合の「フォルダに置いたら自動でラベル付け」Editor拡張の要否
- `XXDatabaseModel` 間で共通化できる部分が増えてきたら、ジェネリックな基底クラス（`AssetDatabaseModel<T>` 等）への統合を検討する
